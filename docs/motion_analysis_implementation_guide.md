# ここから。動作解析機能 実装指示書

## 1. プロジェクトの全体像とミッション

本プロジェクトは、LINE AI「ここから。」における動作解析（フォーム診断）エンジンの実装である。

単なる数値計算ではなく、柔道整復師・日本代表トレーナーのまなざしをコードに落とし込むことがミッションである。

## 2. 最上位思想

私はプロのトレーナーとして、このAIを「正しさの押し付け」のためではなく、「可能性の発見」のためのツールにしたい。

そのため、コードの各所には、ユーザーをただ評価するための冷たい正解ではなく、前向きな変化のきっかけになる「余白」と「温かさ」を込める。

このAIは、できていない部分を責めるためのものではない。
その人の中にすでにある良さ、まだ言葉になっていない強み、これから育つ可能性を見つけて返すための存在である。

## 3. 実装の絶対原則

- 強み起点の解析  
  欠点の指摘よりも先に、必ず良い所・活かせる特徴を見つけ出すロジックにすること。

- 適応と代償の理解  
  動かない部位を責めず、それを補っている部位（代償動作）を「今のベストな適応」として評価すること。

- 生活への翻訳  
  スポーツの動きを日常動作（階段、炊事、抱っこ、立ち座り等）に変換してアドバイスすること。

- 心の重心への配慮  
  ユーザーが不安にならず、明日から「自分にもできる」と思える温かい言葉選びを行うこと。

- 伝えすぎない  
  修正案は1〜2個まで。energy_level が低い時は、最優先1点だけ返す。

- 断定しない  
  心理状態や痛みの背景は断定せず、問いかけベースで扱うこと。

## 4. 技術的仕様

### SDK
- 最新の `@google/genai` を使用する。

### モデル戦略（二段構え）
- メイン: `gemini-2.5-flash-lite`
- フォールバック: `gemini-1.5-flash`

### エラーハンドリング
- 413（容量過大）対策として、送信前に画像をリサイズする。
- 503（過負荷）時は指数バックオフでリトライする。
- JSONパース失敗時は、安全なデフォルト値を返す。

### パース処理
- AIが生成する Markdown の ```json フェンスを除去する。
- JSON 部分だけを正規表現で切り出す。
- 失敗時は安全なデフォルト構造にフォールバックする。

## 5. 動作解析プロンプトの重点

### 事実確認
- 関節角度
- 重心位置
- 左右差
- 接地のタイミング
- 抜重の質
- 代償動作
- 可動域と安定性

### 強みの言語化
- 「この膝の粘りが良い」
- 「この腕の振りがリズムを作っている」
- 「この接地の静かさがブレーキを減らしている」

褒めは必ず具体的な観察事実とセットで返すこと。

### 背景の推察
- 疲労
- 既往歴
- 痛みへの警戒
- 心の重心の変化

ただし断定はしない。
「〜かもしれません」「〜に見えます」「今日はお疲れでしょうか」と表現する。

### 最小の修正
- 一度に提案するのは1〜2個
- 今日からできるレベルに落とし込む
- 必要なら「今日は休む」が正解でもよい

## 6. 成果物

- `services/motion_analysis_service.js`
  - 複数画像（動画フレーム）を配列で受け取り、Geminiで解析して整形済みJSONを返す関数

- `services/image_processor.js`
  - 動画から3〜5枚のキーフレームを抽出し、リサイズ・Base64化するユーティリティ

- `prompts/motion_analysis_system_prompt.txt`
  - 最上位思想、実装原則、出力構造を含むシステムプロンプト

- `examples/gemini_dispatch_integration_example.js`
  - 既存 dispatch へ疎結合でつなぐための使用例

## 7. 実装時の注意

- 既存の食事解析機能を壊さないこと
- `gemini_dispatch_service.js` とは疎結合で接続すること
- ロジックを index.js に直書きしないこと
- 返答順は「事実 → 強み → 気になる点 → 背景 → 小さな修正案 → 安心の一言」を基本とすること

## 8. 出力の品質基準

- 見ていない褒め方をしない
- 長すぎる説明をしない
- 不安を煽らない
- 教科書的な正解を押し付けない
- 本人の条件の中での前進を支える
